# What the owned projects write for themselves that app-kit should hold

A read of every owned project's main, 2026-10-28: what two or more projects wrote separately for the same job, what one project wrote that a practices rule asks every app of its kind to have, and app-kit pieces a project copied or worked around. Each path below is in that project's repository at its main of that day. The harvest of 2026-10-26 (argon-watcher, timescale, urge-surfer, amazon-connector) and the beeline review of 2026-10-28 already filed fourteen tickets in `backlog.md`; this plan does not repeat them, and adds the new evidence for six of them at the end.

The owner's aim, stated on reading the plan: expand the use of app-kit and make the apps consistent. A piece several apps wrote is built into the kit even where the apps holding the copies do not take the kit yet, and those apps' tickets move them onto it.

## What was read

Twenty-eight projects, from their origin's main: advanced-direct, ai-buddy, always-be-closing, amazon-connector, argon-watcher, assay, beeline, buddy-system, collider, creative-strategy, dfract, disk-buddy, fleet, getter, hall-pass, lifeform, matter, metamax, mosquito, move-buddy, perf-buddy, practices, reminder-x, sightline, timescale, urge-surfer, worktron, xplnr. collider (GraphQL and Prisma) and creative-strategy (Next.js) are on an older stack and were read for ideas only. Checkouts of other organizations were not read for this plan.

Eight projects take app-kit, at tags from v0.8.0 (amazon-connector) to v0.19.0 (beeline, perf-buddy's menu bar app); main is at v0.21.0. Twelve web clients take nothing from it: ai-buddy, assay, buddy-system, disk-buddy, lifeform, matter, metamax, mosquito, move-buddy, perf-buddy, reminder-x, worktron. Nor do the command-line tools (dfract, hall-pass, xplnr, assay, perf-buddy's collector) or fleet and practices.

## server-start · app-kit/server/start: a Hono app with the health route, a request log that never prints a query, JSON errors and a clean stop

Goal: nineteen servers start the same way and each differs. Health is /api/health in eleven, /health in five and /healthz in always-be-closing server/src/app.ts:45, while the kit's README example probes /api/health and five of seven railway.json files check it. hono/logger prints each request's path with its query (hono 4.13's middleware/logger takes `url.slice(url.indexOf("/", 8))`), and on an OAuth callback the query is a live sign-in code: argon-watcher server/log.ts:1-20 replaces it (its audit item F-7), while lifeform server/index.ts:27 logs /api/spotify/callback with its `code` (server/routes/spotify.ts:75-76) and ten servers use the bare logger. No server sets app.onError; error bodies are inline everywhere, and lifeform answers validation failures in a second shape (server/routes/discover.ts:667,695). Only lifeform server/index.ts:108-109 and move-buddy server/index.ts:465-466,516-517 stop on SIGTERM. A development CORS setup is copied between ai-buddy server/index.ts:19-24 and buddy-system server/index.ts:11-16, and between disk-buddy server/index.ts:25-31 and metamax server/index.ts:83-88.
app-kit/server/start gives:
- `requestLog()`, hono/logger with every query replaced by `?[redacted]`, exported alone too.
- `appServer({ service })`: a Hono app with requestLog, GET /api/health answering `{ ok, service, commit }`, the commit being the one Railway built from (RAILWAY_GIT_COMMIT_SHA, null elsewhere) so a check can confirm which code production serves, as argon-watcher server/app.ts:36-42 does today; an onError that answers an HTTPException with `err.getResponse()`, as Hono's own default does, so the kit's agent keys keep their `{ error: 'unauthorized' }` (authentication/agent-keys/index.ts:101) and an authorization middleware its WWW-Authenticate header, and logs any other error with its stack and answers 500 `{ error }`; a JSON 404 under /api/.
- `listen(app, { onStop, ...serve })`, which hands Bun.serve every option it is given as it is (hostname, websocket, maxRequestBodySize, idleTimeout, as metamax server/index.ts:292-300 and matter src/server/index.ts:165-173 set them), takes PORT when no port is given, logs the address once, and on SIGTERM or SIGINT stops taking requests, lets open requests finish for a few seconds and then closes what is still open (a live-update stream never ends by itself, and Bun's stop() waits for every connection), runs onStop (a database's close(), a repeating job's stop) and exits. Railway sends SIGKILL at once unless the service sets `deploy.drainingSeconds` (https://docs.railway.com/reference/deployments, read 2026-10-28), which the README's example sets.
serveBuiltPage mounts on it as it does on any Hono app.
Done when: app-kit/server/start exports all three, with hono as an optional peer; server tests through app.request hold the health route with its commit, a logged callback line carrying neither code nor state, agent keys mounted on appServer answering 401 with their own body, an ordinary error's 500 and the /api/ 404; a test starts a real server on port 0 in a child process with a websocket handler and a hostname passed through, opens a websocket and a stream that never ends, sends SIGTERM and finds onStop run and the process gone within the grace; the web fixture's server (web/e2e/serve.ts) is built on it; and the README's server section shows a whole server with openDb, serveBuiltPage, agent keys and the railway.json draining line.
Do not touch: the servers; each moves in its own thread.
Needs: nothing.
Touches: server/start/, web/e2e/serve.ts, test/, package.json exports and peers, README.md.

## test-start-up · Every project's test start-up file is one file in app-kit, the setup skill's

Goal: every `bun test` process keeps its temporary files in a folder of its own outside the system's shared one, as practices' tests rule asks, and the setup skill's "Test start-up file" is the template each project copies; practices' test holds its own copy to that text. Six repositories carry a copy: practices tests/preload.ts and sightline scripts/test-preload.ts are one file with a different root; metamax scripts/test-preload.ts:33 with server/lib/process-test-dir.ts:22-30 and fleet bin/test-setup.ts with bin/test-temp.ts:12 match practices' check line for line; urge-surfer scripts/test-tmp.ts and mosquito server/test-setup.ts refuse a different mode (0o077 against 0o022). app-kit's own test/temporary-folder.ts is a seventh version, with other error words, no shared-folder switch, and a different sweep under `--parallel`. The setup skill then tells a new project to name the kit's file instead of copying the template (a practices thread).
Done when: the preload is exported, the kit's own bunfig.toml loads it by its export name and test/temporary-folder.ts goes, a test runs `bun test` in a scratch project that preloads it and finds TMPDIR under /tmp/<that name>-tests/<pid>, a scoped name gives one folder, a folder another user could write to is refused with its reason, and the README says what a project adds to bunfig.toml.

## ages · One function for how long ago something happened, in the words the menu bar theme uses

Goal: seventeen copies in eleven projects say how long ago something was, each with its own thresholds and words: ai-buddy client/src/features/sync/MachineCard.tsx:18-26, getter client/src/App.tsx:38-43, metamax client/src/features/code/status.ts:58-65 and overview.ts:67-75, mosquito client/src/components/LaundrySettings.tsx:30-36, NodeFaults.tsx:26-33 and RoomControls.tsx:22-27 (90 minutes and 36 hours in one, 48 hours in another), move-buddy client/src/features/migration/move/InsuranceCard.tsx:35-46 and MoveView.tsx:20-27, perf-buddy apps/client/src/pages/Dashboard.tsx:16-22, sightline src/views.ts:72-78 ("N min ago") and src/report.ts:149, and matter's own pair in two client files. The menu bar theme's samples already write ages as "2m ago" and "2h ago" (swift/menu-bar/Sources/menu-bar-snapshots/Samples.swift:43-74). Two copies do another job and keep it: argon-watcher src/lib/time.ts counts only days on purpose, and urge-surfer src/ui/format.ts:23-42 writes "Last night" and "Thursday afternoon". The words are written by hand rather than through Intl.RelativeTimeFormat, whose words change with the locale and the browser's ICU (en-GB writes "2 min ago"). It has no React, so a server's text can use it too.
`age(when, now)` writes "just now" under a minute, "Nm ago" under an hour, "Nh ago" on the same calendar day, "yesterday" on the calendar day before in the reader's time zone, "Nd ago" under a week, then the date in the reader's locale; `useNow()` in app-kit/web ticks once a minute while the page is in view (urge-surfer src/ui/useNow.ts:11-13 is the model), so ages move without each screen keeping a timer.
Done when: `age` is exported where a server can import it without React or MUI and `useNow` from app-kit/web; a unit test holds every threshold on a fixed clock, including a time from late on one evening read early two mornings later, midnight in another time zone, and a time in the future; `useNow` stops ticking while the page is hidden under happy-dom; and the README lists both with the words they write.
Do not touch: the apps' copies; argon-watcher's and urge-surfer's, which do other jobs; the menu bar theme, which takes ages as words from its app.
Needs: nothing.
Touches: a module beside web/ that imports no React, web/, test/, test/exports.test.ts, package.json exports, README.md.

## repeating-jobs · A job on a clock that never runs twice at once, logs its failures, and stops with the server

Goal: argon-watcher server/scheduler.ts:60-90 and reminder-x server/services/scheduler.ts:120-145 each wrote the same guard against setInterval starting a run while the last one goes on (one would double-send alarms, the other change mailboxes twice), with their own log words; lifeform server/index.ts:100-105 and mosquito server/modules/schedule.ts:746 run theirs bare, and metamax wrote an `every` helper three times (server/lib/watch-folder.ts:42, server/live/recap.ts:106, server/live/freeze-watch.ts:116). Bun.cron also never stacks runs, but a throw in it ends the process unless the app listens for unhandled rejections, its stop() does not wait for a run in progress, and it runs on the wall clock in whole minutes; croner and toad-scheduler offer an overrun guard but no stop that waits. app-kit/server gives `every(name, intervalMs, job, { runAtStart })`, which sets the next run only once the last has settled, so two never overlap and nothing is skipped; a throw is logged with the job's name and the next run still happens; and it returns stop(), which waits for a run in progress and is what server-start's onStop calls.
Done when: `every` is exported from app-kit/server, tests on a fake clock hold a slow run never overlapping the next, a throwing job followed by a good run, runAtStart, and stop() waiting for a run in progress; and the README shows it with server-start.
Do not touch: the servers; a lock for several instances, which no app runs today (argon-watcher server/triage/matter-store.ts:111 takes an advisory lock inside one job, which stays the app's).
Needs: server-start, for the stop on shutdown.
Touches: server/, test/, README.md.

## chrome-stand-in · The kit's chrome stand-in covers what the extensions' own copies needed, and refuses the network

Goal: the kit's extension/testing/chrome.ts (116 lines) is used only by amazon-connector test/worker.test.ts:2. always-be-closing test/chrome-shim.js (504 lines, preloaded for every test by its bunfig.toml:4 and imported by 26 test files), Beeline extension/test/chrome-shim.js (282 lines, 25 importers) and perf-buddy apps/chrome-extension/test/chrome-shim.js (63 lines, 2) each wrote their own. Read side by side on 2026-10-28, the kit's fakes the manifest and files, storage get and set, alarms, the profile's account, permissions without origins, and navigator.locks. All three need more, and share a core: tabs (query with address patterns, active and group; get, create, remove, update; events with a way to fire them; always-be-closing's addTab at :110), windows (get, getAll, getLastFocused, update, create), storage with several keys, remove and clear in both areas, runtime messaging (sendMessage, onMessage, onInstalled, onStartup) and a native port fake (Beeline :98-103,260-274), permissions with origins and a way to grant by default (always-be-closing grants at :314-315), identity's onSignInChanged, and alarms clear and getAll. And all three refuse the network in a test (always-be-closing :53-64 records each call and throws unless a handler is set; Beeline :247-257 answers only Google's userinfo), while the kit's sends any address but the extension's own to the real network (chrome.ts:99), so a kit-based test can depend on the internet without anyone seeing it. The rest is one extension's alone: scripting and the toolbar badge (always-be-closing :277-304), declarativeNetRequest, webNavigation and webRequest (Beeline :185-221), getAuthToken (Beeline :117-122), contextMenus. The kit's stand-in gains the shared core and the network refused and recorded unless a test sets a handler, a tab's address left out unless the manifest grants `tabs` or the page's origin (as Chrome does), and a way for an extension's tests to add an area of its own, so the long tail stays in the extension that needs it.
Done when: extension/testing/chrome.ts holds the shared core with unit tests for each method, the network refused by default with a test that a stray fetch fails and is recorded, and the area hook shown by a test that adds one; the kit's own worker tests pass on it; the README's testing section lists what it fakes; and no test address is anything but example.com (Beeline's copy defaults to a real-looking Gmail address).

## focus-tab · The extension worker shows a link in a tab already open on it before it opens one

Goal: practices' rules/extensions.md asks that a link focus a tab already showing its address, raising its window, before it opens a new tab. Beeline's extension/lib/show.js:15-58 does it: a minimized window brought back, a profile with no window given one, and an answer saying which happened. It also skips its own check tabs (isCheckTab) and lets the link through its hold (openUnheld), which only Beeline has; perf-buddy apps/chrome-extension/src/background/index.js:175-222 focuses a tab its daemon names but never opens a link; always-be-closing popup.js:9-19 opens its own pages, which Beeline's http and https check would refuse. extension/worker/show.js takes Beeline's, accepts the extension's own pages beside http and https, and takes two options, a test for tabs to skip and a wrapper around the open, so Beeline can take it in without losing either. Chrome fills in a tab's address only for an extension with the `tabs` permission or host access to that page, and ignores tabs.query's `url` filter without them (https://developer.chrome.com/docs/extensions/reference/api/tabs, read 2026-10-28), so the piece needs one of the two, compares each tab's address itself as Beeline's does (show.js:40-41) rather than filtering by address, and when it can read no tab's address it says so in its answer and logs it once. Beeline and perf-buddy hold `tabs` and broad host access; an extension without them names the new permission to the owner before it takes the piece in, as the rule asks, host access to its own site being the narrower choice when its links go only there.
Done when: extension/worker/show.js exports `showLink(url, { skip, open })`, unit tests against the kit's chrome stand-in hold each answer (existing tab, new tab, new window, the extension's own page, refused address, no access to addresses) and each option, the fixture extension's manifest gains `tabs` and its copy is updated with `app-kit extension copy`, the harness opens a link twice in a hidden Chromium and finds one tab, and the README's extension section lists it with the permission it needs; practices' rule names the kit (a practices thread).
Do not touch: Beeline's and perf-buddy's copies; the permissions of any extension but the fixture.
Needs: chrome-stand-in, for tabs and windows.
Touches: extension/worker/, extension/test/, extension/test/fixture, README.md.

## Not recommended

- A shared lint config or tsconfig base: six .oxlintrc.json files share one core, but the setup skill holds the template every new project starts from, which already solves it.
- The MUI theme copies (ai-buddy, buddy-system, disk-buddy and metamax share one color object): plain-look's tokens and theme cover it, and those apps move onto that.
